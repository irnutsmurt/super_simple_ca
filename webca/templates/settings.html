How this web UI serves itself over HTTPS — and whether Caddy can use it as an ACME CA.

Simplest — fine for browsing the dashboard on a trusted LAN. But Caddy can't auto-renew (ACME) against a plain-HTTP CA — it requires the ACME endpoint over HTTPS. Choose this only if you're not using Caddy/ACME with this CA.

Serve HTTPS from your own tls_cert/tls_key files. Works with Caddy/ACME, but you must re-issue and replace it before it expires — if it lapses, the ACME endpoint goes down and every Caddy renewal breaks.

SSCA issues its own cert and auto-renews it forever — no manual cert, no calendar reminders, no bootstrap loop. Point Caddy (and your DNS) straight at SSCA — by IP, or a DNS record aimed at SSCA rather than through Caddy — and fill in those address(es) below.

Changing this takes effect on the next restart (TLS is bound at startup). Managed mode needs the CA initialized and signable unattended (unencrypted key or persist mode) — the same requirement as ACME.

Off by default (standard ACME lets the old cert expire on its own). When on, a renewal — same account, same host(s) — revokes the cert it replaces, keeping the list tidy. Matches on identical name sets, so a host with genuinely separate certs is unaffected.

Changing enable or the external URL takes effect immediately. Serve the endpoint over HTTPS (e.g. via Caddy) with a cert clients trust.

External Account Binding (EAB) {{ 'required' if acme_cfg.eab_required else 'optional' }}

An EAB credential is a shared secret (a key ID + MAC key) a client must present to register an ACME account — like an API key for enrollment. Issue one per client; revoke it to cut that client off. When Require EAB is on, accounts can't be created without one.

Set the http-01 port per client only if it answers the challenge somewhere other than 80 (e.g. Caddy behind a host that hijacks 80 → 8031; Proxmox answers on 80 so leave it blank). SSCA validates each client's challenges on its own port.

Caddy admin API

⚠️ Make Caddy keep published routes across restarts

Publishing adds routes through Caddy's admin API. By default Caddy re-reads its Caddyfile on restart and drops anything added via the API — so your published services (and their certs) disappear until you re-publish. Run Caddy with --resume so it reloads the last live config instead. First boot still seeds from the Caddyfile; after that, the admin-API state (the autosave) wins.

Docker / Compose — set the command and persist the config dir (that's where autosave.json lives):

command caddy run --config /etc/caddy/Caddyfile --resume
volume caddy_config:/config

Non-container (systemd) — point ExecStart at the same flags:

ExecStart /usr/bin/caddy run --environ --config /etc/caddy/Caddyfile --resume

Heads-up: once an autosave exists, later Caddyfile edits are ignored. To re-seed from the file, delete autosave.json (in the config dir — containers: the /config/caddy/ volume) and restart.
